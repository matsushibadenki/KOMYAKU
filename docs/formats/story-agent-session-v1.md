# Local Story Agent session v1

Status: implemented local host integration; verified through a dedicated macOS Tauri application on 2026-10-15.

`openStoryAgentSession(workspaceId)` lives in the Desktop services layer. It reads authoritative Rust state and captures the current immutable Version, Branch, working revision and exact Snapshot hash. The host retains the returned session and passes **only `session.agent`** to its local Agent adapter.

```js
const session = await openStoryAgentSession(workspaceId);
const answer = await session.agent.query({
  type: 'consistency', pathIds: [routeA, routeB]
});
const proposal = await session.agent.propose(operations);

// Host UI displays the candidate and waits for an explicit author action.
const review = session.review(proposal.proposalId);
showCandidate(review.beforeSnapshotJson, review.snapshotJson);
// In the host's author-confirmation handler:
const result = await session.adopt(review, { label: 'Reviewed change' });
```

## Capabilities and lifecycle

The Agent object exposes only `scope`, `query` and `propose`. It has no adoption, rejection, raw `invoke`, arbitrary Version selector or current-state setter. Query results remain tied to the opened Version; opening a new session is required to work on an adopted Version. A dirty working Snapshot is refused as the basis for an Agent proposal until the author explicitly captures/checkpoints it. Read answers whose immutable hash differs from the session's working Snapshot also fail with `story_agent_checkpoint_required`.

`propose` detaches operations into exact JSON, calls native preview and checks returned identity, revision, hash and full composite validity. The Agent receives only a proposal ID, candidate hash and base Version ID. The host keeps the full candidate for review, with at most eight pending/in-flight proposals. Full Snapshots cross IPC only for opening the host session and deliberate author review, not for each Agent query.

`review` creates an opaque in-process review token. Copying or fabricating the token cannot authorize adoption through the host controller. `reject` removes an unattempted proposal and revokes its review tokens. `close` revokes the session. These are local object capabilities, not a sandbox: the main-window SQL/native privileges already exist, and a hostile extension sharing that environment could call other commands. Untrusted/remote Agents require a separately authenticated and authorized bridge that exposes only the intended tools.

## Native preview and adoption

`preview_story_workspace_proposal` accepts a strict nested proposal:

```text
commandJson: existing bounded Document/Graph operations with expected revision
baseVersionId: exact immutable parent
branchId: expected current Branch
baseSnapshotHash: exact stored base bytes
```

Rust validates the current composite, selection, immutable base hash and equality of the working/base bytes, then derives the candidate using the same native command implementation as ordinary edits. The returned `snapshotJson` and `candidateHash` are generated by Rust. Preview writes no state, history or operation receipt.

`adopt_story_workspace_proposal` accepts `{ proposal, operationId, versionId, candidateHash, label }`. It refuses unknown fields and caller-supplied author/time/parents. It re-derives the candidate and requires the exact reviewed hash. The existing SQLite writer transaction checks revision and Branch/selection/head guards and adopts working state, a single-parent named Version, retained Asset closure, Rust-owned author/time and the durable operation receipt together. An error at the final receipt stage rolls back the whole adoption. This is not a two-parent reviewed Merge.

Receipt replay precedes new state reads and is repeated by the writer. A second identical request that races with preview also checks the winning receipt before returning a stale error. Changing any prepared request field under the operation ID is a collision. New operations with stale guards cannot overwrite later work.

## Uncertain outcomes

The host allocates operation/new-Version IDs once, before its first adoption call. If the response is lost or malformed, it keeps that exact request and only allows retry of that proposal with the same label; switching proposals or rejecting the uncertain one is blocked. Native receipts make repeated requests safe, including after later edits or DB reopen. A successful result is retained and further host retries do not invoke another save.

This low-level controller keeps review tokens process-local. The ordinary editor now uses the durable review journal described below; it persists the candidate and prepared adoption request in Rust/SQLite before invoking adoption. The original packaged Story Agent QA gate remains a test of the low-level controller; the Agent Editor QA gate additionally verifies recovery of unadopted reviews and post-commit uncertain outcomes through the ordinary App.

## Ordinary editor and durable review journal — 2026-10-15

The ordinary local editor includes a compact Agent review panel, translated into English, Japanese and Simplified Chinese. It imports an Agent proposal file shaped as `{ "operations": [...] }`, displays manuscript changes and expandable structural operations, and offers explicit adoption/rejection. No AI provider is called by importing a file. Local Agent adapters can reuse `prepareEditorStoryScope` and `stageStoryAgentReview` rather than requiring a file roundtrip.

Before staging a proposal, the host holds its normal document-mutation gate and saves the current editor checkpoint. It locates the matching composite Workspace or initializes one with the document and an empty Graph. Later ordinary text edits are checkpointed into a new composite Version by `checkpoint_story_agent_document`; Rust reads the stored local draft and validates its compatibility with existing Graph references. A Graph whose Canonical references no longer exist requires explicit repair, not silent deletion of references. Document-only history controls and composite history remain separate until the remaining N3S history/Archive integration.

Production migration 12 adds `story_agent_reviews` and `story_agent_review_assets`. `stage_story_agent_review` validates the native preview, matches its base against the ordinary editor draft and stores the exact proposal/candidate/hash. At most eight active reviews and 64 MiB of active candidate/request bytes are retained per Workspace; document listing is capped at 32 active reviews. Candidate and request fields have independent 24 MiB limits, and candidate prose must fit the ordinary editor's 12 MiB draft limit. The unified retained-Asset view includes unadopted candidates so their attachments cannot be quarantined as unreferenced.

`list_story_agent_reviews(documentId)` returns bounded review identities/statuses. `load_story_agent_review(reviewId)` verifies the immutable base hash, candidate hash and native derivation again before returning the exact before/after snapshots to the host. A restart restores the list and lets the author reopen a review; selection/focus itself is not persisted.

`attempt_story_agent_review(reviewId)` allocates operation/new-Version UUIDs in Rust and durably records the exact adoption JSON before attempting the save. A restart or retry reuses that stored JSON. The existing writer transaction now also verifies the editor's current prose against the review base and atomically updates:

- working Document/Graph state, composite Version, parent, Branch/selection and native author/time;
- exact operation receipt;
- ordinary editor draft/revision and document metadata/Asset links;
- review status `adopted` and its adopted editor revision.

The review's temporary Asset links are released only after the immutable Version owns the candidate closure. A failure during review completion rolls back all adoption changes, while the previously prepared request remains available for retry. A rejected review revokes an already-prepared in-flight adoption at the final transaction gate; an already-adopted review cannot be rejected as though it had never been saved.

The panel blocks editing while an adoption outcome is uncertain. It refreshes durable status before preparing a retry: if already adopted, it must not checkpoint the old visible text over the committed draft. If only `review`/`attempting`, it saves current edits first, allowing Rust to refuse a stale base instead of losing newer prose. Known stale-state failures restore editing and ask for a new proposal. After restart, an adopted review is absent from the pending list and the ordinary editor loads the committed draft directly.

An external Agent still receives only the intended query/proposal capabilities. The existing main-window SQL capability means these local controllers do not authenticate or isolate hostile plugins. External/provider-backed transports remain separate work. Pending reviews are local workflow records, not part of Archive v3 yet; do not treat an exported archive as a backup of the review queue.

## Verification and remaining integration

The dedicated `KOMYAKU Story Agent QA` bundle uses real WebView → production adapter → Tauri ACL/IPC → Rust → SQLite. A deterministic Agent fixture issues all four query types, proposes a repair, waits for a real native-screen author click, simulates response loss only after the native transaction returns, retries, rejects an old session's proposal, and verifies old/new answers. Full process restart verifies the adopted Snapshot without another write. See the [native verification record](../testing/story-workspace-native.md#local-agent-session-and-packaged-ipc--2026-10-15).

Ordinary editor review controls and the local durable queue are implemented. Remote/provider-backed transports, two-parent composite Merge and native Archive v3 import/export remain separate ROADMAP work. The QA fixtures do not invoke an AI provider or require credentials.
